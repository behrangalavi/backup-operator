# 0001. CRDs after all: `BackupSource` / `BackupDestination` / `BackupRecipient`, credentials stay in Secrets

**Status:** Accepted.

The project started with the opposite decision ("labelling a Secret is the entire contract") to avoid the installation step, the version-skew surface and the documentation surface a CRD brings. Three things made that decision expire. (1) The annotation vocabulary grew to ~20 string-typed keys with no schema; the documented coping strategy was "a typo falls back to the default", which is exactly the failure mode a backup tool must not have — a misspelled `restore-verification-mode` silently ran no verification. (2) There was no place for status: last run, last success, verifier verdict all had to be reconstructed from `meta.json` into Prometheus, and `kubectl get` showed nothing. The Settings wizard ended up writing a ConfigMap nothing read, precisely because there was no typed object for the operator to consume. (3) Secret-as-config forced every GitOps user to seal schedule and retention together with the password, so config reviews were impossible and UI edits of the config implied Secret write access. The CRDs fix all three: OpenAPI enums/ranges plus CEL rules reject bad specs at admission; `status` carries conditions and run-level fields written change-only by the operator; the spec is plain reviewable YAML while `credentialsSecretRef` (with optional `passwordKey`/`usernameKey`) points at a Secret that can be the database chart's own. What stayed the same is everything below the discovery layer: both flatteners produce the identical `secrets.Source` / `secrets.Destination` structs, so the pipeline, analyzer, storage backends, verifiers, `meta.json` and the metrics did not change; the storage `Data` map is keyed exactly like the old destination Secret so no backend was touched. Cost accepted: a hard cut at 0.x (no dual-mode period) with `backup-restore migrate` as the one-shot converter — a transition period would have meant two parsers, two reconcile branches and two documentation tables for a product that is still pre-1.0. Second-order wins the CRD move made cheap: the operator no longer caches Secrets at all (`client.CacheOptions.DisableFor`), so it holds only the Secrets it reads by name instead of an informer over every Secret in the namespace; the worker and operator RBAC lost `secrets: list/watch`; and `targetName`/`pathPrefix` traversal is now rejected by the API server, not only by our parser.
