# 0008. CronJob deletion is ownership-checked, not name-only

**Status:** Superseded. Superseded by [0001](0001-crds-after-all-backupsource-backupdestination-backuprecipien.md). The label-removal delete path is gone with the labels; CronJob cleanup is owner-reference GC from the `BackupSource` ([0006](0006-ownerreference-for-cascade-delete.md)).

`deleteCronJobIfOwned` used to `Delete` `backup-<secretName>` by name outright. The name is not proof of ownership: an operator running their own unrelated CronJob that happens to collide with that name (or a hash-suffix collision between two long Secret names mapping to the same managed name) would have their CronJob destroyed the moment a same-named Secret lost its role label. The fix Gets the object first, verifies a controller OwnerReference back to *this* Secret's UID (`ownedBySecret`, the same reference `buildCronJob` sets and K8s GC keys on), and deletes under a `client.Preconditions{UID}` so a same-named object recreated between Get and Delete is not clobbered. UID — not name, not the managed-by label — is the authoritative signal, since a foreign object cannot forge an OwnerReference to a UID it doesn't know. Regression-tested: owned→deleted, unowned→left, wrong-owner-UID→left.
