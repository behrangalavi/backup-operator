# 0017. Three binaries, one image

**Status:** Accepted.

Two-binary distribution per service is awkward. A single image with two `cmd/` entrypoints means one CI build, one registry tag, one version to track. Revisited the split question: the image is ~530 MB, ~430 MB of which is DB client tooling (`pg_dump` from PGDG, MySQL/MariaDB client, mongo-tools) that *only the worker* uses — the operator never shells out to a dump tool. A slim operator image (~100 MB) was considered and rejected. The headline benefit (faster operator pulls) largely evaporates because the worker mandates the fat image on every node it runs on (cached via `IfNotPresent`), so a separate operator image *adds* an image to the node rather than replacing one — node disk goes up, not down, unless operator and worker land on disjoint nodes. The security argument is also weak: the operator already holds Secret CRUD (the DB credentials themselves), so a `pg_dump` binary sitting next to them is a marginal attack-surface increase against what a compromised operator can already do. Against those near-zero gains sit permanent distribution costs: two tags, two Helm image refs, doubled digest pinning, version-sync in the release workflow. If image size becomes a real problem, the right lever is trimming the *single* image (drop unused client packages, `--no-install-recommends`, layer cleanup) — that shrinks it for both pods without the split's complexity. (The original "30 MB binary-size difference is irrelevant" rationale was on the wrong axis — the real cost was never the binaries, it was the client tooling, and the conclusion still holds once you reason about node-level image caching.)
