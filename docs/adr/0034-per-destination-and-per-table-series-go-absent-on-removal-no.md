# 0034. Per-destination and per-table series go absent on removal, not sticky

**Status:** Accepted. Written under the labelled-Secret model; Secret/annotation names map to CRD fields as listed in [the mapping](README.md#pre-crd-names).

The `MetricsRefresher` already dropped a target's whole series set when its Source Secret vanished (`trackedTargets` → `DeleteTargetMetrics`), but it had no equivalent for the *sub-target* label dimensions. When a destination was dropped from a source's `backup.mogenius.io/destinations` allow-list, its `retention_last_status{target,destination}` / `destination_failed{...}` / scrub series kept reporting their last value forever — a removed backup target looked permanently healthy (or permanently failing). Same for a table dropped from the schema: `table_row_count{target,table}` stuck at the last count, so a deleted table's rows never went to zero, they just froze. The refresher now tracks, per target, the destination and table label-sets it exposed last tick (`trackedSeries`), and on the next tick deletes the series for any destination no longer in the allow-list (`DeleteDestinationMetrics`) or any table no longer in the schema (`DeleteTableMetric`). Destination reconciliation runs up front from the source's allow-list (a pure config function, independent of whether run data exists yet), so a removed destination is cleaned even when the remaining destinations are currently empty. Table reconciliation runs only on a tick that has *authoritative* stats (a successful run with a `Stats` block) — a failed run leaves the prior table set sticky rather than spuriously deleting every table because stats collection was skipped. Trade-off accepted: this is "absent" semantics (the series disappears), which means PromQL `... unless` / `absent()` queries see the change but a naive `== 0` alert won't — consistent with how `DeleteTargetMetrics` already behaves for whole-target removal.
