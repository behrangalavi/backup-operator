# 0046. Pool lazy-init guarded by `sync.Once`; SFTP keepalive goroutine bound to connection lifetime

**Status:** Accepted.

Two concurrency hardening fixes on the operator-side storage path. (1) `StorageScrubber` and `MetricsRefresher` both lazily build their `StoragePool` when none is wired (tests, non-production paths). The old `if s.Pool == nil { s.Pool = NewStoragePool(...) }` ran inside `scrub`/`refresh`, which fan out to concurrent per-destination goroutines — the unguarded nil-check + assign was a data race on the lazy path (the `go test -race` flagged it only intermittently because production wires the pool externally). Replaced with an `ensurePool()` that does the build inside `poolOnce.Do`, idempotent and race-free; an externally-wired pool is left untouched. (2) The SFTP `dial` keepalive goroutine watched only `ctx.Done()` and a 30s ticker. For a pooled `sftpStorage` dialed under the operator's long-lived context, the client can be closed (pool eviction, credential rotation, server drop) while ctx is still alive — the goroutine then survived until the next tick happened to fail `SendRequest`, leaking one goroutine per dial for up to a full interval. Fix: a second goroutine blocks on `client.Wait()` and closes a `closed` channel the instant the connection dies; the keepalive loop selects on `closed` (plus ctx for prompt shutdown), tying its lifetime exactly to the connection. Note: the earlier ADR's "future Reconnect-on-Error wrapper at the pool layer" is moot for SFTP/FTPS as currently written — both `storage.Storage` impls dial a fresh connection per call (`dial(ctx)` inside every Upload/List/Get/Delete), so the pool caches only the config object, not a live connection. There is no persistent pooled connection to go stale; liveness is inherent in the per-call dial. The pool's handshake-saving benefit applies only via the `WithSession` batch path (retention), not the per-call metric/scrub reads.
