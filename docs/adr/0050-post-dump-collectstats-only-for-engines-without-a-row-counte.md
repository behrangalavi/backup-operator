# 0050. Post-dump `CollectStats` only for engines without a row counter (mongo/redis)

**Status:** Accepted.

The pipeline collected stats both before AND after the dump. `postStats` feeds exactly one path in `BuildVerification`: the `!hasDump && hasPre && hasPost` branch, which is the *only* verdict path for mongo/redis (their archive/RDB formats can't be row-counted in-stream). For SQL engines the row counter already saw every INSERT/COPY row, so the verdict comes from `dumpCounts`-vs-`preStats` and `postStats` is purely informational meta content (`PostStats` / per-table `PostDumpRows`) that nothing downstream consumes for a decision — not the analyzer (it compares against `preStats`), not any metric, not the UI. Empty-dump detection for SQL also uses only `preStats` + `dumpCounts`. So gating the second collection on `!rowCounter.Active()` saves a full `CollectStats` roundtrip (a `pg_stat_user_tables` / `INFORMATION_SCHEMA` query) on every SQL backup — real load at 10k+ daily runs — with a verdict-identical result. Observable change: SQL `meta.json` no longer carries the `postStats` block (it's `omitempty`), but the stream-observed `dumpRowCounts` it keeps are more authoritative than a post-dump estimate anyway. Mongo/redis behaviour is byte-identical.
