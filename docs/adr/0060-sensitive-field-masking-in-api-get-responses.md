# 0060. Sensitive field masking in API GET responses

**Status:** Accepted.

Passwords, SSH private keys, and S3 secret keys are returned as `***` in GET endpoints. The UI sends these values only on create/update. This prevents accidental exposure through browser dev tools, network logging, or screen sharing — even without an auth proxy. The mask set is now `secrets.CredentialKeys(type)` — the same table the flattener and the migration tool use — so a backend's credential keys cannot be forgotten in one place and remembered in another. Historically the mask set had to mirror the destination Secret schema by hand ([§6.5](../crds.md#65-destination-credentials-secret)): it covered `password`, `ssh-private-key`, `secret-access-key`, `access-key-id`, `account-key` (Azure), and `service-account-json` (GCS). The S3 `access-key-id` was previously absent from the set and leaked in plaintext on GET — masked now because, while an access-key id is semi-identifying rather than secret, returning it to an unauthenticated client narrows credential reconnaissance for no benefit. The Azure `account-key` and the full GCS `service-account-json` were also absent and leaked verbatim — those are outright secrets (full read/write to the bucket holding every dump), so their omission was a real credential-disclosure bug, not a reconnaissance nicety. The recurring lesson: adding a storage backend must extend this mask set in lockstep with the backend's credential keys — deriving the set from each backend's declared secret keys would make the omission impossible.
