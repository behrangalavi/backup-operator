# 0061. CSRF defence on mutating UI endpoints via `csrfMiddleware`

**Status:** Accepted.

The UI has no built-in auth ([§3.1](../getting-started.md#31-securing-the-ui-with-an-authentication-proxy)) and is commonly fronted by a cookie-based auth proxy; without a CSRF check a malicious page could drive `DELETE /api/destinations/...`, trigger jobs, or rotate age keys through the victim's browser. The middleware (in the global chain, so new endpoints inherit it) lets GET/HEAD/OPTIONS through, then rejects mutating requests whose `Sec-Fetch-Site` is `cross-site`/`same-site`. `Sec-Fetch-Site` is set by all modern browsers and computed client-side, so it survives reverse proxies. For older browsers that omit it but send `Origin`, the Origin host must match `Host` (or `X-Forwarded-Host` for the proxy deployment). Non-browser clients (curl, the restore CLI, monitoring) send neither header and pass through unchanged — this narrows the *browser* attack surface, it does not replace the auth proxy. Token-based CSRF (synchroniser tokens) was rejected: it needs server-side session state the stateless UI doesn't have, and the header-based check is sufficient because the SPA is same-origin. A `Content-Type: application/json` requirement was rejected because bodyless mutations (DELETE, `POST /api/trigger/`) legitimately omit it.
