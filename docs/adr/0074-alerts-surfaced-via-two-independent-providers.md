# 0074. Alerts surfaced via two independent providers

**Status:** Accepted. Written under the labelled-Secret model; Secret/annotation names map to CRD fields as listed in [the mapping](README.md#pre-crd-names).

`internal/alerts.PrometheusProvider` queries `/api/v1/alerts` on the configured Prometheus and filters by `alertname=~"^Backup.*"`; `internal/alerts.LocalProvider` re-evaluates the shipped PrometheusRule conditions inline against the operator's gathered metric registry. The UI handler exposes whichever is configured (Prometheus preferred, local as fallback chained automatically). This keeps the UI useful before kube-prometheus-stack is wired up — most of the value of alerts is "what's on fire right now", which we can answer locally — while preserving the audit-grade path through Prometheus → Alertmanager once it's set up. The two evaluators are deliberately independent: there is no shared PromQL evaluator, the local rules are ~100 lines of Go that mirror the YAML in `values.yaml`. Keep both in sync when adding a rule. The LocalProvider mirrors every *problem-signalling* rule (`BackupOverdue`, `DestinationFailing`, `DumpSizeCollapsed`, `SchemaChanged`, `CharsetChanged`, `StorageCorrupted`, `RetentionFailing`, `AnomaliesAppearing`, `LastRunFailed`, `RestoreVerificationFailed`, `RestoreVerificationStale`); only `BackupSucceeded` is intentionally omitted (it is a positive heartbeat, not a firing condition). The restore-verification rules are keyed on the `mode` label, which the Alert schema has no field for, so it is folded into the summary text — matching how the PrometheusProvider surfaces the rule's `mode` annotation. The `Source` field on each Alert (`"prometheus"` vs `"local"`) tells the UI to show a "for: not honored" disclaimer when in local mode. (Earlier the LocalProvider mirrored only nine rules and silently omitted the two restore-verification rules — a critical `RestoreVerificationFailed` was invisible on the only alert surface a Prometheus-less deployment has; both are now mirrored.)
