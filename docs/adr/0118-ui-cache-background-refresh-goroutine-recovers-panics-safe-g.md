# 0118. UI cache background-refresh goroutine recovers panics (`safe.Goroutine`)

**Status:** Accepted.

The stale-while-revalidate cache (`ui/cache.go`) spawns a goroutine in `getOrRefreshAsync` that runs a caller-supplied `load()` closure doing storage I/O + `meta.json` parsing. That goroutine was the one long-lived operator goroutine NOT wrapped in `safe.Goroutine` — every other one already was (the §-above `safe.Goroutine` ADR established the contract: "long-lived operator goroutines must recover"). `net/http` recovers panics *per request*, but NOT in a goroutine a handler spawns: the SSE-driven dashboard polls `/api/targets` and `/api/dashboard/heatmap` ~every 10 s, each fans out background refreshes, and a panic in `load()` (nil deref on a malformed meta, an unexpected storage response) crashed the **whole operator pod** — observed in the field as "the operator restarts sometimes". Fix: `defer safe.Goroutine(c.log, "ui-cache-refresh", c.name+":"+key)` at the top of the goroutine. Second, subtler fix bundled in: the `delete(c.loading, key)` that clears the per-key dedup flag ran *after* `load()`, so even a recovered panic would have pinned the key as "loading" forever (it would never refresh again — silent stale-forever). Moved into a `defer` so it always runs. Defer order is load-bearing (LIFO): `safe.Goroutine` is registered first so it runs last, recovering after the loading-flag and semaphore-slot defers have released. The cache carries a `log logr.Logger` + `name string` purely for this recovery log; a zero `logr.Logger` is a no-op sink, so tests that build caches without one still recover (just don't log).
