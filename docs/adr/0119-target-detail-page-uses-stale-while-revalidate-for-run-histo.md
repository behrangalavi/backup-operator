# 0119. Target detail page uses stale-while-revalidate for run history, mirroring the dashboard

**Status:** Accepted.

Run history is the *only* storage-probing fetch on the detail page (the backend `target()` probes each destination, up to 12 s apiece). The page used to `await` it inline before writing ANY content — so clicking a source showed a blank spinner for many seconds even though the summary cards (config, latest run) come from the fast, non-blocking `/api/targets` read, and a language switch (`setLang` → re-render) re-fired the whole slow probe. Two symptoms, one cause: the slow probe sat on the synchronous render path. The dashboard already solved this for its charts via `_fleetSummary`/`_slowProbes` caches (render from cache, refresh in background, repaint via SSE); the detail page now does the same. New `_targetRuns` cache (30 s TTL, keyed by target name) + per-name in-flight guard. `renderTargetDetail` renders the summary immediately and drops a `<div id="target-runs-region">`; `fetchTargetRuns` refreshes in the background and repaints ONLY that region, never the whole page (so an in-flight probe can't yank the summary away). A purely presentational re-render — language switch, sort, an unrelated SSE tick — reuses the cache and never re-probes storage; that is what made re-translating the page slow. A probe is kicked only when the cache is for a different target, expired, or invalidated (SSE `meta_changed`/`backup_triggered` set `_targetRuns.lastFetch = 0`). **Loading vs. failed vs. genuinely-empty:** a flat runs array can't distinguish "probe timed out → empty" from "this target has never run". The fix: `targetRunsRegionHTML` shows a spinner while in-flight, and when the result is empty it checks whether the target's `Latest` meta exists — if it does, at least one run MUST exist, so an empty list there is a probe failure (shows "run history unavailable" + a Retry button), not the misleading "No runs" it used to show. Only a target with no `Latest` and a clean fetch renders "No runs". Trade-off: the detail page can briefly show stale run history after a new backup lands; the SSE-driven invalidation + repaint corrects it within seconds — same stale-window trade the dashboard already accepts. The backend `target()` stays blocking-but-bounded (its own ADR above) — this change takes it off the *frontend's* critical render path, it doesn't change the endpoint.
