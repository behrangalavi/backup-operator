# 0120. Meta-upload-on-all-destinations failure fails the run, not silently succeeds

**Status:** Accepted.

`uploadMeta` is best-effort (retries 3× per destination) but used to be fire-and-forget: if the dump uploaded but every destination then failed the small `meta.json` upload, the pipeline still called `SetLastRunStatus(true)` and returned nil. Because the metrics refresher, UI, and restore listing ALL key off `meta.json`, that run was invisible — a phantom backup (dump objects present, no sidecar, un-analyzable, only surfaced 36 h later as `BackupOverdue`). Fix: `uploadMeta` now returns `(attempted, succeeded)`. `succeeded==0 && attempted>0` is treated as a run failure (`SetLastRunStatus(false)`, `BackupFailed` Event, worker exits 1) so K8s retries with a fresh timestamp — a visible failure beats a silent phantom. Considered alternatives: (a) re-upload meta on the next run only — rejected, leaves a window where the dump is unrecoverable-by-tooling; (b) keep best-effort but emit a metric — rejected because worker metrics aren't scraped (the whole reason the refresher reconstructs from storage). A *partial* failure (sidecar reached ≥1 destination) keeps the run successful — it's still discoverable — and emits `BackupMetaPartial` (warning) so per-destination divergence is auditable. Meta-upload failures now log at Error, not Info. Trade-off accepted: the orphan dumps from a fully-failed attempt linger until retention prunes them by timestamp.
