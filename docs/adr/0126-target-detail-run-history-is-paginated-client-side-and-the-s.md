# 0126. Target detail run history is paginated client-side and the size-trend chart is capped

**Status:** Accepted.

A high-frequency schedule (e.g. `*/15`) with long retention accumulates tens of thousands of runs; the detail page rendered one table row (~11 cells) AND one size-chart `<circle>` per run, which froze the browser. Both are now bounded WITHOUT changing the fetch: the run-history table pages client-side over the already-cached `_targetRuns` array (`RUN_HISTORY_PAGE_SIZE`=50, prev/next + "{from}–{to} of {total}"), and the size-trend chart receives only the newest `MAX_TREND_POINTS` (365) points with a "most recent N" sub-label when truncated. The status heatmap is left full — it aggregates by day (≤91 cells) so run count drives a cheap JS loop, not DOM. The fetch is deliberately NOT bounded: `target()`, `fleetHeatmap`, and `estimateDuration` share the `name@dest` `runsCache` and the heatmap needs its full day-window, so a count-bound fetch would either truncate the heatmap or require a second cache population that regresses the common retention==window case (see the dropped "meta.List limit/since" investigation). Pagination is pure rendering: `gotoRunHistoryPage` repaints only `#target-runs-region` from cache, never refetches; `_runHistoryPage` resets when the viewed target changes. Trade-off: older runs aren't all visible at once, but the total count is shown and every run remains reachable by paging (and via the restore CLI). The full run array stays in memory — this caps render cost, not data availability.
