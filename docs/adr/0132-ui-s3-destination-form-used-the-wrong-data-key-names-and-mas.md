# 0132. UI S3 destination form used the wrong data-key names, and masked credentials must be preserved-on-empty across all backends

**Status:** Accepted.

The S3 form wrote `access-key` / `secret-key`, but the backend requires `access-key-id` / `secret-access-key` (`storage/s3/s3.go`) — so *every* S3 destination created through the UI produced a Secret the backend rejected at first use. It also hard-required `endpoint` (wrong for AWS, which infers the endpoint from the region) and offered no `path-style` toggle (needed for MinIO). Fixed the key names, made `endpoint` optional with a hint, and added a `path-style` checkbox. Coupled fix: once [§18](../adr/README.md)'s masking change made Azure `account-key` and GCS `service-account-json` return as `***` on GET, the edit form (which leaves masked fields blank and relies on PUT-merge to preserve them) would have *deleted* those credentials on save unless the key is in the frontend's `DEST_SENSITIVE_KEYS` set — so `access-key-id`, `account-key`, and `service-account-json` were added there, and the sensitive credential inputs dropped their `required` attribute (which would otherwise block edit-mode submit when the field is intentionally blank), matching the long-standing SFTP-credential convention of "label carries `*`, no `required` attribute".
