# 0133. Phase-2 verifier DB pod uses a per-run random password, not a compile-time constant

**Status:** Accepted.

All four restore engines hard-coded `verifierPassword = "verifier-ephemeral"` (redis had its own copy) into the ephemeral pod's root credential, the probe, the restore CLI env, and the smoke-query DSN. The pod holds a full copy of the source's data and — with the ephemeral-pod-spawn RBAC enabled — is reachable on the flat pod network for the minutes-to-hours of a restore, so any workload in any namespace could connect with a credential that was effectively public and read everything, bypassing the age-encryption model. Fix: `NewEngine` generates a fresh 16-byte hex password per verification run (per `factory.New` → `restore.New` → `NewEngine`, which is per-run) and injects it into each engine struct; the probe is now an engine-bound closure and `PodSpec`/`Restore`/`SmokeQueries`/`sanitiseStderr` all read the instance field. A leaked or observed password now grants access to a single short-lived pod holding one run's data, never the fleet. This does not remove the value of a NetworkPolicy on the verifier pod (defence-in-depth), but it closes the "known credential" hole on its own. Regression-tested (`TestNewEngine_UniquePasswords`, `TestRandomPassword_UniqueAndHex`).
